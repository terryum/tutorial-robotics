# Robotics book authoring contract

This is documentation production, not guided learning. Do not initialize or change learner progress, install heavy stacks, execute devices, or push.

Read the catalog, runner dispatch, selected implementation, tests and public verification before drafting. Keep existing lesson H2 headings and add detail under H3. For an executable lesson, guide the reader through what they will learn and why, a prediction before running, the code and inputs, the observed result, one change and its meaning, then a comprehension question. State the inputs that stay fixed and tell the reader where to find evidence in the output. Define symbols, units, coordinate frames and array shapes where the reader first needs them. Label worked calculations as calculations. Prefer relative source links that resolve in GitHub and MkDocs. Keep claims about execution within the evidence for that host and stack.

Draft Korean first, review the technical meaning and readability, then write English. Apply the Korean Markdown guidance in `~/.codex/AGENTS.md` to every Korean Markdown file you touch. State who acts, what they do and when. Include preconditions and the result to check where the reader needs them. Use natural particles, finite endings in prose and established technical terms. Preserve facts, numbers, terms, quotations, links, commands and code blocks unless the approved work changes them. Include these same requirements in every author and reviewer assignment and its acceptance criteria. During integration, read each changed Korean file in full, compare the diff against the preserved material, and check that the English counterpart uses the same conditions, numbers and commands.

In common foundations, have the agent present validated evidence before asking the comprehension question. Give readers the plot, rendering or comparison values they need to answer from their execution. Show how to resume the result and question, and place review and completion after the learner's answer or request to finish. Keep explicit host diagnostics outside the learning sequence.

Keep ACT contract, VLA mock, optimizer execution, independent policy performance and hardware readiness separate. Missing runtime is capability-unavailable. Scaffolded physical lessons teach preparation only: runner refuses execution; do not suggest variant trials or finish without device evidence. An offline paper calculation is permissible, never a physical action. WS names never authorize runtime capability. Mac Core scope is 32 lessons plus deployment and offline sink; matched-engine analysis needs separately produced PhysX evidence.

Concept chapter slugs: simulation, kinematics, control-contact, reinforcement-learning, data-imitation, robot-hands, mobile-motion, ros, physx, vla, deployment-hardware. Link from each lesson Reader route to the appropriate ../concepts/<slug>.md. In core-01, place this link under Further reading after the checkpoint and put catalog metadata in a collapsed section there. All concept pages pair English/Korean with identical equations, conditions and numbers. Preserve language switches.

Worker writes only assigned run output files, mirroring docs/{en,ko}/..., plus a review note in its output folder. Main integrates after independent review. No product files by Reviewer or QA. Main owns shared contracts, generator, README and config. Use inherited model/effort and no nested delegation. Max parent + 3 children. Retry review corrections at most twice; unresolved mandatory defects block completion. Record passed/failed/not_run honestly. Review is agent reader-perspective evaluation, never a human learning study.
