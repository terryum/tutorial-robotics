# 수동 실습 경험에서 도출한 로봇 튜토리얼 개선 가이드

작성일: 2026-09-11

대상: public·private 양쪽의 교재 작성자 및 Codex·Claude Code 안내 에이전트

범위: 공개 가능한 공통 학습 경험, 개선 요구사항, 교재 본문 예시

## 1. 목적과 적용 원칙

수동 로봇 시뮬레이션 실습에서 학습자는 직접 명령을 입력하고, 화면과 출력을 확인하며 추가 질문을 했다. 반복해서 드러난 문제는 실행 실패보다 **무엇을 조작하고 있는지, 무엇이 계산되는지, 그 결과가 실물과 어떻게 연결되는지**를 이해하기 어려웠다는 점이다.

이 문서는 그 경험을 로봇에 독립적인 교재 개선안으로 정리한다. public과 private 모두에 적용하며, 특정 비공개 로봇의 이름·관절·제한·인터페이스·원시 로그·내부 경로는 포함하지 않는다. 로봇별 적용 기록은 해당 저장소 안에 별도로 둔다.

학습자의 핵심 요구는 다음과 같다.

- 에이전트가 설명해주어야만 진행되는 부분을 GitHub 교재에도 남긴다.
- 카메라 조작과 터미널 사용을 선수 지식으로 가정하지 않는다.
- 명령의 문법, 입력의 물리적 의미, 출력의 해석을 연결한다.
- 기구학·동역학·제어·통신을 구분하고 실물 적용까지 설명한다.
- 수식은 영문 변수명 나열 대신 렌더링된 기호, 한글 뜻, 단위, 계산 예시로 전달한다.
- 모든 관절을 반복하기보다 대표 동작으로 개념을 확인하고 선택 실습을 제공한다.

이 문서는 **개선 작업을 안내하는 설계 문서**다. 아래의 제안 기능·본문 초안을 현재 모든 lesson에 구현된 기능으로 해석하지 않는다. 새로운 수업 이수나 하드웨어 검증을 기록하지 않는다.

## 2. 수동 학습 과정에서 관찰한 문제

질문은 원문 전체가 아닌 의미 중심의 요약이다. 아래는 개인별 로봇 시험 보고서가 아니라 학습 과정의 일반화된 기록이다.

| 학습 흐름 | 학습자의 질문·경험 | 교재가 먼저 제공했어야 할 내용 |
|---|---|---|
| 환경 준비 | 새 터미널에서 직접 실행하는가, 에이전트에게 실행을 맡기는가? | 수행 주체, 결과 전달 방식, 실행 중 대기하는 프로그램의 의미 |
| 여러 창 실행 | 어느 터미널이 시뮬레이터이고 어느 것이 RViz인가? | 문자와 역할을 함께 쓰는 터미널 표 |
| 상태 표시 | 기준 좌표계 이름은 무슨 뜻인가? | 원점·축·Fixed Frame·모델 기준 자세 |
| 단발 목표 | 발행 로그는 나오지만 움직임이 안 보임 | 발행 성공과 실제 상태 변화는 다른 증거라는 설명 |
| 화면 관찰 | 확대·축소·시점 이동 방법을 모름 | 첫 움직임 전에 카메라 조작 연습 |
| 두 뷰어 비교 | 한쪽에서는 보이는데 다른 쪽에서는 안 보이는 것 같음 | 현재값→TF→표시 순서의 진단 |
| 시각적 복잡도 | 좌표축이 로봇을 가림 | TF 표시 숨기기와 데이터 발행의 차이 |
| 작은 운동 | 더 큰 각도로 보아야 이해하기 쉬움 | 모델 제한, 카메라, 전후 비교, 수치 관측의 조합 |
| 반복량 | 모든 관절을 다 해야 하는가? | 필수 대표 실습과 선택 실습 |
| 반복 입력 | Python 명령의 각 부분을 알고 싶음 | 모듈 실행·ROS 인자·파라미터·토픽 해설 |
| 코드 출처 | 예제가 튜토리얼 코드인가, 외부 로봇 코드인가? | 프로젝트·공통 라이브러리·vendor의 출처 지도 |
| 시스템 이해 | 같은 목표가 두 뷰어를 각각 움직이는가? | 목표 생성, 물리 계산, 상태 전달, FK, 표시의 분리 |
| 계산 이해 | 관절각을 FK로 그리면 끝 아닌가? | 목표 각도와 현재 각도, FK와 동역학의 차이 |
| 초기화 | 서비스 호출의 타입과 빈 요청은 무엇인가? | 요청·응답과 토픽의 차이 |
| 실물 이행 | 같은 명령과 PD를 쓰면 실물도 동일하게 움직이는가? | 실제 센서 피드백·명령 모드·모델 오차·제한 |
| 이론 이해 | tau 같은 텍스트만으로 수식을 이해하기 어려움 | 기호·한글 이름·단위·숫자 대입 |
| 장애 비교 | 멈춘 자세가 초기 자세와 비슷해 구별하기 어려움 | 식별 가능한 기준 상태와 마지막 수신 시각 |
| 재개 | 오늘 확인한 지점부터 다음에 이어가고 싶음 | 완료·미완료·제안만 한 실행을 분리한 기록 |

관절과 입력을 바꾼 뒤 화면과 상태가 연결되는 경험은 학습에 도움이 됐다. 반면 긴 배열을 반복해서 복사하거나, 비슷한 운동을 모두 수행하는 것은 새 개념을 배우는 속도를 늦췄다. 교재는 **명령을 실행했다는 사실과 학습 목표를 이해했다는 사실을 따로 확인**해야 한다.

## 4. 권장 수업 구조

기존 catalog의 capability와 선수 관계를 유지한다. 다음은 모든 수업을 한 번에 실행하라는 새 과정이 아니라, 관련 lesson 안의 설명과 실습을 배치하는 원칙이다.

1. **무엇을 배울지:** 입력·상태·출력의 전체 지도를 먼저 보여준다.
2. **어디에서 실행할지:** 터미널·환경·프로세스·기존 발행원 확인을 설명한다.
3. **어떻게 볼지:** 카메라, 시점, 축 표시, 관찰할 부위를 준비한다.
4. **무엇을 읽을지:** 이름·단위·현재값·시각·주기를 확인한다.
5. **무엇을 바꿀지:** 하나의 물리적 파라미터를 바꾸고 결과를 예측한다.
6. **왜 바뀌는지:** 관찰 직후 수식과 해당 코드 위치에 연결한다.
7. **실물에서는 무엇이 다른지:** 측정 피드백과 인터페이스 차이를 설명한다.
8. **문제가 생기면 무엇을 볼지:** 장애·차단·복구를 분리한다.
9. **무엇을 확인했는지:** 숫자와 시각적 관찰, 미확인 항목을 기록한다.

각 단계의 고정 구조는 **목적 → 명령 해설 → 예상 결과 → 직접 관찰 → 해석 → 이상 시 확인**으로 한다. 터미널의 추가 질문은 해당 본문의 누락 여부를 재검토할 근거로 남긴다.

## 5. 교재 본문에 사용할 공통 설명 예시

아래는 공개 표준 도구와 일반 모델에 관한 설명이다. 실제 실행 명령·주기·제한·초기값은 선택한 공개 또는 private backend에서 확인해 채운다.

### 5.1. 터미널 역할과 복사하기 쉬운 명령

| 이름 | 역할 | 실행 중의 특징 |
|---|---|---|
| A — 시뮬레이터 | 물리 계산·상태 발행 | 일반적으로 계속 실행되어 프롬프트가 돌아오지 않음 |
| B — 표시 | robot_state_publisher·RViz | 모델과 좌표계 표시 |
| C — 입력·관측 | 단발 입력, 상태 조회, 반복 발행 | 한 번에 하나의 전경 프로그램 사용 |
| D — 추가 관측 | 반복 발행을 유지하면서 동시에 조회할 때 | 필요한 시점에 추가 |

터미널 글자만 쓰지 않고 역할을 함께 쓴다. 새 셸에는 해당 환경 활성화가 필요하며, 이미 활성화한 C를 재사용할 때는 준비 명령을 불필요하게 반복하지 않는다.

실행 명령은 각각 한 줄로 제공하고 셸 프롬프트나 줄 연결 문자를 붙이지 않는다. 의사코드·자리표시자와 실행 가능한 명령을 분리한다. 아래는 특정 로봇 이름이 없는 ROS 읽기 명령의 예다.

~~~bash
ros2 topic list -t
~~~

설명할 문법은 `python -m`, `--ros-args`, `-p 이름:=값`, `ros2 topic pub --once`, `ros2 service call`이다. `topic` 같은 파라미터는 개별 노드가 정의하는 것이므로 모든 노드에 공통으로 존재한다고 설명하지 않는다.

서비스 예제에는 **이름 / 타입 / 요청 / 응답 / 구현이 하는 일**을 모두 표시한다. Trigger의 빈 요청 `{}` 자체가 reset을 뜻하는 것은 아니다. reset 서비스가 있다면 상태·목표·시간 중 무엇을 초기화하는지 구현을 확인한다.

### 5.2. MuJoCo와 RViz의 카메라 조작

3D 영역 위에서 마우스를 조작한다. RViz는 **Move Camera**와 **Orbit** 모드를 기준으로 설명한다.

| 기능 | MuJoCo viewer | RViz Orbit |
|---|---|---|
| 확대·축소 | 휠 돌리기 | 휠 돌리기 |
| 둘러보기 | 왼쪽 버튼 드래그 | 왼쪽 버튼 드래그 |
| 화면 안에서 시점 이동 | 오른쪽 버튼 드래그 | 가운데 휠 버튼 드래그 |
| 다른 줌 방법 | 가운데 버튼 드래그 | 오른쪽 버튼 드래그 |
| 보조 기능 | Shift+오른쪽 드래그: 수평면 이동, F1: 도움말 | m: Move Camera |

MuJoCo의 Ctrl+드래그는 선택 물체에 힘을 가하는 조작에 사용될 수 있으므로 카메라 연습은 Ctrl 없이 수행한다. Python passive viewer의 물리 진행은 사용자 코드가 담당하므로 Space를 정지 보장으로 안내하지 않는다. [MuJoCo 조작 문서](https://mujoco.readthedocs.io/en/latest/programming/samples.html#simulate), [ROS Jazzy RViz 안내](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/Tutorials/Intermediate/RViz/RViz-User-Guide/RViz-User-Guide.rst)

RViz에 TF display가 활성화되어 있다면 Displays의 **TF 체크** 또는 **Show Axes / Show Arrows**로 표시를 숨길 수 있다. RobotModel은 켜둔다. 표시는 숨겨도 다른 노드의 TF 발행까지 중단되는 것은 아니다.

첫 운동 전에 정면·측면을 바꿔 보고, 손·끝단처럼 방향이 구별되는 부분을 확대한다. 관절 회전축과 카메라가 나란하거나 형상이 대칭이면 수치가 바뀌어도 화면 변화가 작을 수 있다.

### 5.3. ROS·토픽·TF·기준 좌표계

ROS 2는 로봇 프로그램을 연결하는 통신·라이브러리·도구 체계다. MuJoCo 자체는 ROS 없이 실행할 수 있고, ROS는 MuJoCo 없이 실제 센서·로봇의 데이터를 전달할 수 있다.

**토픽**은 이름과 메시지 타입을 가진 전달 통로이며 발행자가 보내고 구독자가 받는다. 토픽 자체가 FK나 동역학을 계산하지는 않는다. [ROS 2 토픽](https://raw.githubusercontent.com/ros2/ros2_documentation/jazzy/source/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.rst)

**TF**는 시간에 따른 좌표계 간 위치·방향 관계를 관리하고 조회하는 체계다. robot_state_publisher는 URDF와 관절 상태로 링크 변환을 만들며, 동적·고정 변환은 각각 /tf와 /tf_static으로 전달한다. [robot_state_publisher](https://raw.githubusercontent.com/ros/robot_state_publisher/ros2/README.md)

**Fixed Frame**은 RViz가 데이터를 표시하는 기준이다. odom은 주행 추정에 흔히 사용하는 좌표계 이름이지만, 예제가 고정 변환만 제공한다면 실제 주행 추정이나 자유 베이스 운동을 검증한 것은 아니다. 선택한 launch가 world·odom·base 사이를 어떻게 연결하는지 그림으로 보여준다.

다음은 **위치 목표를 받아 동역학으로 움직이는 bridge를 선택한 경우**의 구조다. 모든 시뮬레이터가 이 경로를 사용하는 것은 아니다.

~~~mermaid
flowchart TD
    A["목표 생성기"] -->|"명령 토픽: 목표 각도"| B["bridge와 위치 서보"]
    B -->|"토크"| C["MuJoCo 동역학: 다음 상태 계산"]
    C --> D["MuJoCo 내부 상태로 화면 표시"]
    C -->|"상태 토픽: 현재 각도와 속도"| E["robot_state_publisher + URDF"]
    E -->|"TF: 링크 위치와 방향"| F["RViz 화면 표시"]
~~~

각 교재는 명령 토픽과 상태 토픽의 **이름·타입·발행자·구독자·물리적 의미**를 표로 제공한다. 같은 메시지 타입을 목표와 상태 양쪽에 사용한다면 의미가 다르다는 점을 강조한다. 목표 한 점의 반복 발행과 JointTrajectory/action으로 궤적을 전달하는 방식도 구분한다.

### 5.4. 목표·시뮬레이션·실측 상태를 다른 기호로 표시

| 기호 | 한글 뜻 | 회전 관절 단위 |
|---|---|---|
| $q_{\mathrm{target}}$ | 목표 관절각 | rad |
| $q_{\mathrm{sim}}$ | 시뮬레이터가 계산한 현재 관절각 | rad |
| $q_{\mathrm{measured}}$ | 센서에서 측정·환산한 현재 관절각 | rad |
| $\dot q$ | 각속도 | rad/s |
| $\ddot q$ | 각가속도 | rad/s² |
| $\tau$ | 관절 토크 | N·m |

직선 관절은 위치 m, 속도 m/s, 구동력 N으로 별도 표기한다. 모든 관절 값을 rad로 해석하지 않는다.

관절 이름으로 상태를 찾고 배열 순서를 고정으로 가정하지 않는다. 과학 표기법의 작은 값과 의미 있는 변위를 구분한다. effort가 빈 배열이면 미제공이며 힘·토크 0의 측정값이 아니다.

### 5.5. FK만으로 충분한 경우와 동역학이 필요한 경우

이미 관절각이 있고 자세만 표시하려면 **순기구학(FK)**으로 충분하다. 각 링크 사이 변환을 곱해 끝단 자세를 구한다.

$$
{}^{0}T_n(\mathbf q)
= {}^{0}T_1(q_1)\,{}^{1}T_2(q_2)\cdots{}^{n-1}T_n(q_n)
$$

$\,{}^{a}T_b$는 좌표계 b의 좌표를 a로 표현하는 4×4 동차변환으로, 회전과 이동을 포함한다. $\mathbf q$는 관절 좌표를 모은 벡터다. FK는 주어진 자세를 계산하며 힘·도달 시간·추종 가능성을 결정하지 않는다.

동역학은 현재 상태와 힘으로 다음 상태를 계산한다. 고정 베이스 회전 관절계를 설명하기 위한 표준 형태는 다음과 같다.

$$
M(\mathbf q)\ddot{\mathbf q}
C(\mathbf q,\dot{\mathbf q})\dot{\mathbf q}
\mathbf g(\mathbf q)
=\boldsymbol{\tau}_{\mathrm{act}}
+\boldsymbol{\tau}_{\mathrm{passive}}
+J(\mathbf q)^\mathsf{T}\mathbf f_{\mathrm{ext}}
$$

- $M$: 관절 공간 관성 행렬. $C\dot{\mathbf q}$: 코리올리·원심 항.
- $\mathbf g$: 중력을 상쇄하는 토크 항.
- $\boldsymbol{\tau}_{\mathrm{act}}$: actuator 토크.
- $\boldsymbol{\tau}_{\mathrm{passive}}$: 감쇠·스프링 등 수동 토크.
- $J^\mathsf{T}\mathbf f_{\mathrm{ext}}$: 외부 힘·모멘트가 만드는 관절 토크.

자유 베이스·쿼터니언·제약을 포함하는 MuJoCo 일반식에서는 위치 좌표와 속도 좌표의 차원이 다를 수도 있다. 실제 엔진은 선택된 timestep과 적분기로 상태를 갱신한다. [MuJoCo 계산 원리](https://mujoco.readthedocs.io/en/stable/computation/index.html#general-framework)

교재에는 선택한 구현의 **계산 모드**를 반드시 적는다.

| 모드 | 실제 하는 일 | 주장할 수 없는 것 |
|---|---|---|
| 기구학 애니메이션 | 관절 위치를 지정하고 FK로 표시 | 힘에 따른 추종·지연·접촉 반응 |
| 간소화한 제어 모델 | 명시한 방정식으로 오차·응답 계산 | 전체 로봇의 동역학을 검증했다는 주장 |
| MuJoCo 동역학 | 모델의 actuator·질량·관성·설정으로 상태 갱신 | 모델링하지 않은 현실 요소의 검증 |
| 상태 재생 | 기록된 상태를 읽어 표시 | 새로운 명령에 대한 물리 반응 |

MuJoCo를 사용한다는 이름만으로 동역학을 수행한다고 단정하지 않는다. 코드가 위치를 직접 지정하는지, 제어 입력을 설정하고 물리 step을 수행하는지 확인한다. 중력·접촉이 꺼져 있어도 다른 물리 계산이 남을 수 있으므로 각각의 설정을 명시한다.

### 5.6. 위치 입력과 토크 생성

MuJoCo position actuator는 각도를 목표로 받아 힘을 생성할 수 있다. 단위 gear의 단일 회전 관절에서 제한 적용 전의 단순화한 식은 다음과 같다.

$$
\tau_{\mathrm{act}}
=K_p(q_{\mathrm{target}}-q_{\mathrm{sim}})
-K_v\dot q_{\mathrm{sim}}
$$

$K_p$는 위치 오차 게인(N·m/rad), $K_v$는 속도 감쇠 게인(N·m·s/rad)이다. 실제 모델에는 힘 제한 등의 추가 조건이 적용될 수 있다. 이 식은 현재 속도를 감쇠하는 위치 서보이며, 별도 목표 속도를 추종하는 일반 PD와 구분한다. [MuJoCo position actuator](https://mujoco.readthedocs.io/en/stable/XMLreference.html#actuator-position)

**설명용 예시이며 어느 로봇의 설정값도 아니다:** 목표 0.2 rad, 현재 0.16 rad, 속도 0 rad/s, $K_p=10$ N·m/rad라면,

$$
e=0.2-0.16=0.04\ \mathrm{rad},\qquad
\tau_{\mathrm{act}}=10\times0.04=0.4\ \mathrm{N\,m}
$$

현재 위치를 목표로 즉시 바꾸는 대신, 계산된 토크와 모델로 다음 상태를 구한다. 목표와 현재값이 정착 후 거의 같아도 두 값이 처음부터 복사된 것은 아닐 수 있다.

코드 지도에는 **입력 변수 → 제어식 → 물리 step → 읽는 상태 → 발행 메시지**를 연결한다. 출력 메시지에 토크가 포함되는지 별도로 확인한다. 엔진 내부에서 토크를 계산하는 것과 ROS로 토크를 발행하는 것은 다르다.

### 5.7. 사인파의 진폭·주파수와 여러 종류의 주기

중심각 $q_0$를 포함한 일반적인 목표는 다음과 같다.

$$
q_{\mathrm{target}}(t)=q_0+A\sin(2\pi ft),\qquad T=\frac{1}{f}
$$

$A$는 진폭(rad), $f$는 왕복 주파수(Hz), $t$는 시간(s), $T$는 한 왕복 시간(s)이다. 중심이 0인지 현재 자세인지 구현에 따라 명시한다. 목표 범위 $[q_0-A,q_0+A]$가 모델 제한 안인지 확인한다.

$$
\dot q_{\mathrm{target}}=2\pi fA\cos(2\pi ft),\qquad
\ddot q_{\mathrm{target}}=-(2\pi f)^2A\sin(2\pi ft)
$$

같은 주파수에서 진폭을 두 배로 하면 목표 범위가 두 배다. 같은 진폭에서 주파수를 두 배로 하면 왕복 시간은 절반, 최대 목표 속도는 두 배, 최대 목표 가속도는 네 배다. 실제 추종 성능과 하드웨어 속도 제한은 별도로 확인한다.

권장 비교는 **기준 A,f → 진폭 비교 2A,f → 주파수 비교 A,2f**다. 마지막 실험을 기준 실험과 비교해야 주파수만의 효과를 설명할 수 있다.

왕복 주파수, 목표 발행 주기, 물리 step 주기, 상태 발행·수신 주기, 화면 갱신 주기는 서로 다르다. 교재의 선택한 backend에서 각 값을 확인해 표에 넣고, 한 주기를 측정했다고 나머지까지 검증했다고 쓰지 않는다.

### 5.8. 실물에서는 센서 피드백을 사용한다

상위 목표 생성기를 재사용할 수 있어도 실제 명령 인터페이스와 제어 모드는 맞춰야 한다. 시뮬레이션의 토크 시퀀스를 실물에 그대로 재생하는 방식에는 실제 오차를 스스로 보정할 장치가 부족하다.

실측 상태를 쓰는 일반적인 토크 제어 구조는 다음과 같다. 이는 개념식이며 특정 제조사의 내부 제어기를 단정하는 식이 아니다.

$$
\boldsymbol{\tau}_{\mathrm{cmd}}
=K_p(\mathbf q_{\mathrm{target}}-\mathbf q_{\mathrm{measured}})
+K_d(\dot{\mathbf q}_{\mathrm{target}}-\dot{\mathbf q}_{\mathrm{measured}})
+\boldsymbol{\tau}_{\mathrm{ff}}
$$

$K_d$는 속도 오차 게인, $\boldsymbol{\tau}_{\mathrm{ff}}$는 중력 보상 등 모델로 예상한 선행 토크다. 모델이 완벽하지 않으므로 실제 오차에 대한 피드백과 결합한다. [Modern Robotics의 feedforward와 feedback](https://modernrobotics.northwestern.edu/nu-gm-book-resource/11-4-motion-control-with-torque-or-force-inputs-part-3-of-3/)

~~~mermaid
flowchart LR
    A["목표 각도와 속도"] --> B["제어기: 목표와 실측 비교"]
    B --> C["모터 드라이브와 실제 로봇"]
    C --> D["센서와 상태 추정"]
    D -->|"실측 피드백"| B
    D --> E["관절 상태 → FK → RViz"]
~~~

| 질문 | 교재가 구분할 것 |
|---|---|
| 위치 명령인가, 토크 명령인가? | 위치 명령이면 하위 제어기가 추종하며, 토크 명령이면 외부 제어기의 책임 범위가 달라짐 |
| 엔코더 값은 관절각인가? | 모터측/관절측, 감속비, 영점, 방향, 유격·탄성의 영향 |
| 토크와 전류는 같은가? | 단위와 물리량이 다름. 이상화한 모터의 관계는 $\tau_{\mathrm{motor}}\approx k_t i$이며 실제 관절에는 감속비·효율 등이 관여 |
| RViz는 무엇을 표시하는가? | 실물 확인에는 목표나 시뮬레이션 값이 아니라 실측·추정 상태를 표시 |
| 제어식이 같으면 결과도 같은가? | 게인·지연·모델·제한·하중에 따라 추종과 안정성이 달라짐 |

$k_t$는 모터 토크 상수(N·m/A), $i$는 전류(A)다. 실제 전류 정의·제어 모드·명령 단위는 제조사 자료로 확인한다.

모델 차이를 전부 “외부 노이즈”로 설명하지 않는다. 팔을 미는 외란, 센서 오차, 질량·마찰의 모델 불일치, 통신 지연, 구동기 포화는 다른 문제다.

중력 보상 없이 단일 관절 PD로 정지 자세를 유지하는 단순 모델에서는 다음 평형이 가능하다.

$$
K_p(q_{\mathrm{target}}-q_{\mathrm{steady}})=g(q_{\mathrm{steady}})
$$

중력을 버티는 토크를 만들기 위해 위치 오차가 남을 수 있다는 뜻이다. 피드백이 있다는 이유로 모든 오차가 사라지는 것은 아니다. [중력 아래 PD의 정상상태 오차](https://modernrobotics.northwestern.edu/nu-gm-book-resource/11-4-motion-control-with-torque-or-force-inputs-part-2-of-3/)

실물 적용 설명은 제조사 인터페이스·상태 계약·제한·정지/복구 검증으로 연결하고 [안전 절차](07_SAFETY.md)를 따른다. 시뮬레이션 수치나 설명용 게인을 실물 기본 설정으로 복사하지 않는다.

## 6. 관측과 장애 실습을 개선하는 방법

### 6.1. 화면이 안 움직일 때의 진단 순서

1. **발행:** 입력을 실제로 보냈는가? 발행 로그는 수신·도달을 보장하지 않는다.
2. **경로:** 토픽·타입·QoS·domain·구독자·중복 발행원을 확인한다.
3. **상태:** 해당 이름의 현재값과 새 stamp가 바뀌는가?
4. **TF:** 부모→자식 변환이 기대 방향으로 바뀌는가?
5. **표시:** Fixed Frame, RobotModel, 카메라, 축 표시를 확인한다.

상태나 TF 수치가 정상이어도 육안 확인이 안 됐다면 “시각 확인 미완료”라고 남긴다. 목표를 무조건 키우지 않는다.

권장 관측 표는 **관절 이름 / 목표 / 현재 / 오차 / 속도 / 마지막 수신 나이**다. 목표와 상태의 시각을 맞추며, ROS 시각과 로컬 monotonic 시각 또는 서로 다른 호스트의 시계를 무작정 빼지 않는다.

주기 통계의 과거 샘플과 새 수신을 구분한다. 오래된 데이터는 현재 상태처럼 표시하지 않는다. 그래프를 추가할 때는 목표와 현재값을 같은 시간축에 그리고, 오차와 수신 중단도 표시한다.

### 6.2. 장애마다 무엇이 멈추는지 명시

| 중단 대상 | 관측해야 할 것 | 교재의 해석 기준 |
|---|---|---|
| 목표 발행기 | 목표 갱신, 마지막 목표, 상태 수신 | 마지막 목표 유지·timeout 등 선택한 backend의 실제 계약 확인 |
| 시뮬레이터 | 새 상태, TF 시각, 화면 잔류 | 화면에 로봇이 남아 있어도 새 상태 수신을 뜻하지 않음 |
| 상태 mock | 정상 수신 이력 뒤 stale | 처음부터 미수신인 시험과 구분 |
| 안전 검사기·watchdog | 거부 이유, 출력 차단, 재승인 상태 | 검사기 판정과 물리 정지를 구분 |
| 실물 컨트롤러·통신 | 제조사가 정한 정지·유지·복구 | 시뮬레이션 결과로 대체하지 않음 |

초기 자세와 구별되는 기준 자세를 사용하고 수치도 기록한다. reset, 목표 발행 종료, 계산 중단, 물리 정지를 같은 “정지”로 부르지 않는다.

mock E-stop 또는 watchdog을 제공하는 교재는 그 결과가 **실제 어느 출력 경로에 연결되는지** 보여줘야 한다. 연결되지 않은 검사 결과로 시뮬레이터나 실물 정지가 검증됐다고 주장하지 않는다. 차단 해소와 실행 재승인도 별도 단계로 설명한다.

## 7. GitHub 수식과 에이전트 안내 기준

GitHub에서는 인라인 `$...$`와 독립 블록 `$$...$$` 또는 `math` 코드 블록으로 수식을 렌더링할 수 있다. 본문의 식은 실제 수식 표기로 작성했다. [GitHub 수식 작성](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)

1. 최초 기호에는 한글 이름과 단위를 쓴다. 예: “$\tau$는 토크, 단위는 N·m”.
2. 코드 변수와 수학 기호를 구분한다. 예: 코드 `q_target`, 수식 $q_{\mathrm{target}}$.
3. 목표·시뮬레이션·실측의 아래첨자를 유지한다.
4. 식 아래에 한글 해석과 숫자 대입을 넣는다.
5. 설명용 수치와 모델에서 읽은 수치를 명확히 구분한다.
6. 단순화한 식의 가정을 적고 실제 구현과의 차이를 설명한다.
7. 터미널에서 수식이 렌더링되지 않으면 물리량의 한글 이름으로 풀어 쓰고 GitHub 상세 절을 연결한다.
8. GitHub에서 수식·Mermaid 렌더링과 링크를 별도로 확인한다. 소스 구문 확인만으로 화면 검증을 완료했다고 쓰지 않는다.

| GitHub 교재 | Codex·Claude Code의 실습 안내 |
|---|---|
| 구조도·이론·기호표·출처·예시 출력 | 현재 단계의 목적과 한 줄 명령 |
| GUI 조작표와 주석 그림 | 현재 화면에 맞춘 조작 안내 |
| 필수·선택 실습과 예상 관찰 | 사용자 확인을 기다리고 다음 단계 선택 |
| 정확한 구현·제한·실물 적용 범위 | 확인된 사실과 추측을 구분 |
| 오류 분기와 복구 절차 | 실제 오류에 필요한 진단만 실행 |
| 학습·검증 기준 | 실행 성공과 이해 여부를 따로 확인 |

## 9. public과 private에 함께 적용하는 작업 방식

공통 개념과 편집 기준은 이 문서를 기준으로 공유한다. public의 재현 예시는 공개 소스·배포 조건이 확인된 모델이나 자체 제작한 단순 관절 모델을 사용한다. private에서는 동일한 설명 구조에 해당 모델의 확인된 정보를 채운다.

각 저장소별 적용표에는 다음을 기록한다.

| 항목 | 작성할 내용 |
|---|---|
| 모델·코드 출처 | 공개 여부·pin·라이선스, tutorial/core/vendor 경계 |
| 실행 수준 | 간소화한 모델/FK/물리 엔진/재생/실물 중 무엇인지 |
| 인터페이스 | 실제 실행 파일·토픽·메시지·서비스, 입력과 출력 의미 |
| 모델 가정 | 초기 자세·제한·중력·접촉·구동 모드·베이스 처리 |
| 관측 | 모델에 맞는 부위·방향·단위·시점, 상태 이름 매핑 |
| 실물 연결 | 제조사 근거와 미확인 항목, 피드백·정지·재승인 |
| 검증 상태 | 실행 확인·육안 확인·미실행·미확인 |

private 상세 기록을 public 예제로 바꾸는 작업은 이름만 치환하는 것으로 끝내지 않는다. 공개 모델의 관절 축·제한·제어 모드와 실제 코드에서 다시 확인한다. 양쪽 모두에서 **이 문서의 일반 식이 해당 backend의 실제 구현과 같은지**를 검토한다.

권장 후속 작업 단위:

1. 공통 교재 구조와 카메라·명령·용어 설명을 개선한다.
2. 각 저장소의 기존 예제에서 대표 동작과 이름 기반 관측을 확인한다.
3. 구현이 지원하는 물리 파라미터를 선택해 Try it과 수식·그래프를 연결한다.
4. 실물·장애 설명을 해당 계약에 맞게 보강한다.
5. 새 독자가 에이전트의 추가 설명 없이 수행하는 reader test를 진행한다.

## 10. 완료 기준과 다음 실습을 위한 기록 형식

- [ ] 첫 동작 전에 카메라와 표시 설정을 스스로 조작한다.
- [ ] 각 명령의 실행 주체·문법·단위·종료 방법을 설명한다.
- [ ] 목표 발행, 현재값 도달, TF 반영, 육안 관찰을 따로 확인한다.
- [ ] 목표·현재·실측과 FK·동역학·통신을 구분한다.
- [ ] 사인파의 범위·주기·미분과 실제 속도 제한의 차이를 설명한다.
- [ ] 각 수식에 기호·단위·가정·숫자 예시가 있다.
- [ ] 모델 기반 계산과 실제 센서 피드백을 구분한다.
- [ ] same API/PD가 같은 움직임을 보장하지 않음을 설명한다.
- [ ] 명령 중단·상태 중단·검사기 차단·물리 정지를 구분한다.
- [ ] 공개 문서가 비공개 자산이나 연결 권한 없이 이해·재현 가능하다.
- [ ] 기존 자동 검증, 대화형 화면 검증, 실물 검증을 별도 상태로 남긴다.

세션 기록에는 **실제로 보낸 입력 / 관찰한 값과 화면 / 질문과 보충 설명 / 미실행 제안 / 남은 프로세스 / 다음 시작점**을 남긴다. 원시 로그와 사용자 환경 정보는 해당 저장소의 ignored 로컬 기록에 둔다. 다음 세션에서 관절 반복을 다시 시작할지, 중단·안전 검사부터 이어갈지 명시한다.
