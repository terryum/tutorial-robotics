Read [the common workflow](../../../agent/workflow.md), especially **Prompt-first installation and start invitation**, before generic URL/install/start requests. Inspect the actual checkout's language README, AGENTS/CLAUDE, catalog and bootstrap script. Clone into a non-conflicting directory or reuse the correct repository without reset, branch switch or automatic update. If newly cloned local skills are undiscovered from the parent cwd, read their checkout paths explicitly; never rewrite global settings.

Start with `sh bootstrap.sh --plan`, which works without Python/pal and writes no state. Show native OS/architecture, disk, missing tools, purpose, location and commands. On an existing checkout, run the current verification/import/platform checks below first. If they pass, reuse the working Core environment and skip `--apply`; do not resync/reinstall it each time the prompt is pasted, since `uv sync --no-dev` can prune development extras. If Core setup/repair is actually necessary, the generic install-and-start request already authorizes the displayed minimal ordinary Core `--apply`; do not add another ordinary plan-approval question. Verify again afterward; missing or unsupported requirements remain blocked. An audit/readiness-only request never applies setup. Actual tool/network permissions and EULA consent still apply. Preserve existing environments; system packages, GPU/ROS/Isaac, large models, firmware and real motion retain their separate rules.

Verify with the checkout's `.venv/bin/pal host detect --json`, `.venv/bin/pal setup verify --profile core --json` and actual Python 3.12 plus all declared Core and plotting/image imports (NumPy, MuJoCo, gymnasium, SciPy, Matplotlib, Pillow/`PIL.Image`) as specified by the workflow, without creating plots or running lessons. The Core profile alone checks only three dependencies; the complete native-platform/JSON/import gate is required both before skip-apply and after necessary repair. Inspect exit status and `profile`, `ready`, `missing_capabilities`, `capability_status` and native `host` fields. The script supports Darwin/arm64 and Linux/x86_64; do not invent native Windows readiness. Missing/unverified facts block the ready claim. A previous receipt or a final “Ready” line is not sufficient.

Generic preparation ends with the exact fresh-learner invitation **첫번째 튜토리얼을 띄울 준비가 되었습니다. 시작하시겠습니까?** / **The first tutorial is ready to open. Would you like to start?** and waits for an actual reply before opening/navigating or executing the lesson. Saved learning progress gets a resume invitation. A completed T00 diagnostic alone counts as diagnostic history; never reset it to manufacture a first lesson. An enabled `.local/personal-progress.json` registration with missing/unverified/stale `.local/personal-progress-cache.json` means unknown history, not empty history: use the canonical workflow's distinct history-check invitation, never the fresh-lesson claim. Cache response uses `schema_version=1` and `lessons`; a fallback empty list or `sync.status=pending` cannot prove a new learner, and no universal freshness TTL is specified by the adapter. An explicit T00 request authorizes the diagnostic after readiness. Quoted prompts in authoring work do not trigger setup.

Before the start reply, inspect on-disk progress/session/browser state only; no `pal course init`, course/lesson CLI exchange, lesson run/review/finish, comparison or viewer. Bootstrap environment artifacts and `.local/bootstrap-verification.json` are allowed; learner-state initialization is not. Defer the script's printed course-init/next suggestions. After an actual affirmative reply, recheck state/readiness. If registration is enabled, first resolve history through the normal registered helper flow, inspect success/pending and reread resulting progress/session; only then choose the saved phase/eligible lesson, or initialize/select core-01 if genuinely new. Unresolved/pending history remains unknown and blocks any fresh-learner assumption. Never initialize Core or select the first lesson before that resolution. Enter the canonical one-lesson workflow after selection. A cleared/new chat repeats filesystem/readiness discovery and preserves saved language; it never assumes activation/cwd or erases learner history. Learner evidence stays under ignored `.local/`; do not auto-commit or share it.
